## 结论只用四个词

| 词 | 含义 |
|---|---|
| 保留 | 通过预注册的判定规则，进入前瞻记录 |
| 拒绝 | 可信地证伪，写明适用范围 |
| 证据不足 | 测了，但证据既不能支持也不能否定 |
| 未测成 | 测量本身有问题（常量冒充结论、参数没被读到、样本地板达不到等），不算证伪，可以重开 |

任务卡的 DONE、DROPPED 只表示工程状态，不表示研究结论。研究结论以 `ledger.md` 为准。

## 评级

| 级 | 含义 |
|---|---|
| A 可信 | 看结果前预注册；DQ 通过且 PIT；计成本；有真正的留出样本或足量前瞻样本；试验次数公开；可从记录的 commit 复现 |
| B 有条件可用 | 历史检验做得规范（有预注册、试验可数），但窗口被反复用过或样本小 |
| C 弱 | 事后设计、变体多且没计数、门槛看结果再定、代理或非 PIT 数据、DQ 不明或失败 |
| D 不能当结论 | 只有工程或合同 PASS；数据被污染；后来发现有 bug；或已被推翻 |

## 以后一个研究问题怎么走

评估台建好后启用，细节以 TRADING-2565 的需求文档为准。

1. Owner 定问题。同时进行的问题数不设上限（TRADING-2567）；假阳性靠评估台跨问题累计试验次数、抬高门槛来控制。
2. 写 `research/<问题ID>/prereg.yaml`：问题、问题类型（决定窗口角色）、数据快照 id、基准、成本、主指标、判定规则、样本地板及可达性检查、试验上限、停止条件。
3. Owner 确认，记为一个 `Owner-Decision`，prereg 随一次 ship 进 main。
4. 策略代码只给出每日目标权重；执行滞后、成本、指标、基准都由评估台负责。每次运行自动登记在 `research/<问题ID>/runs/`，失败的也算。
5. 核验：没碰评估台和基准；运行次数没超上限；结论符合预注册规则。
6. 写 `research/<问题ID>/decision.md`，结论用上面四个词。保留的进前瞻记录；拒绝的进 `negative_results.md`（人审后更新）。
